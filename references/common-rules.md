# 共通運用ルール・QA手順

全プロジェクト（KIX1/KSW/STACK等）で共通する運用ルールと品質保証手順。プロジェクト固有フォーマット・翻訳ルールは `projects/<project>.md` を優先。本ファイルは全プロジェクトに適用される下位ルール。

## 1. ドキュメント保持変換の原則

- 原文DOCXのコピーから作業。局所挿入でバイリンガル化し、再構築しない。
- 英語原文を厳密保持。技術的英語修正は別リビジョン作業。
- バイリンガル挿入はべき等：既存日本語を検出し、上書き時に2度注入しない。
- ユーザー編集済みバイリンガルファイルを改訂する場合、原文ではなく**そのファイル**を変換ベースにする。レビュアー承認の英語修正・段落並替・用語・フォーマットを保持。
- 表・結合セル・ナンバリング・チェックボックス・スタイル・ヘッダ/フッタ・ブックマーク・リレーションシップ・画像・図・埋込オブジェクトを保持。
- ネイティブSmartArt：同じシェイプ内の英語の下に別段落として日本語を追加。
- ラスターフローチャート/図：元の寸法・色・形状・コネクタ・順序・グループ化・機器タグを保持したバイリンガル置換を作成。英語先行、日本語はその直下。
- ラスターのバイリンガル化は**元画像への重ね描き（overlay）を既定**とする（`scripts/build_flowchart_bilingual.py`、easyocr + Pillow、SOP-501/903検証）。フル再描画は色崩れ・レイアウト崩れリスクのある最終手段。手順：easyocr(`Reader(['en'], gpu=False)`)で英語ラベルbbox抽出 → 非白色マスク `~((r>230)&(g>230)&(b>230))` の連結成分で色箱矩形検出 → 各箱の英語直下に日本語を重ねる → `zipfile`で`word/media/imageN.*`を差し替え（ファイル名・rels不変）。
- overlay位置決めの二重座標系（SOP-501/903事故の教訓）：水平は**実際の色箱矩形**で中心寄せ・ピル背景を箱境界でクリップ（OCRテキストbboxは箱より狭く、中心に使うとはみ出す）。垂直は**OCR英語テキスト下端Y+4px**（箱下端Yはテキストから~30px下で英日が離れる）。箱色検出に `(channel>200)` を使わない（紫(111,47,161)・青(47,85,151)・緑(84,130,53)は全チャンネル<200で検出漏れ）。日本語はMeiryo 11px、箱幅-12px超過時10→9px自動縮小、白文字+黒4方向縁取り、画像下端超過時キャンバス延長。
- コネクタは管理対象。再作成後に各コネクタを計数・視点検。線形ブロックは中心線を共有し隣接ブロック間に1本の直線。装飾的エルボ・重複セグメント・最終ブロックに続入/貫通する線を追加しない（原文にある場合を除く）。
- 変換後、メディア・図・インラインシェイプ・表・関連パッケージパーツの数を原文/出力で比較。DOCX ZIP整合性をテスト。

## 2. Word修復ファイルの取扱（全プロジェクト共通）

Wordが「読み取れない内容」を報告して修復/再保存した場合：

- 修復ファイルを権威あるパッケージベースラインとする。
- 次リビジョンを**修復ファイルから**作成。原文/故障バイリンガル/ビルダースクリプトから再構築しない。
- Wordが書き直した `document.xml`/`numbering.xml`/設定/ヘッダ/フッタ/カスタムXML/関連パーツを保持。局所編集のみ適用。
- 未修復ファイルから `document.xml` 等を戻さない。

## 3. リファレンス階層（参照が矛盾する場合）

1. 検証済み機器ラベル・承認図・OEM用語・法定/安全要件。
2. 英語原文とSME確認の操作意図。
3. 複数の承認済み文書で一貫して反復される用語。
4. 本スキルの共通ルール（本ファイル）。
5. プロジェクト別リビング翻訳基盤（`projects/<project>.md`）。
6. 単一の過去翻訳。既存するという理由だけで強い証拠を覆さない。

## 4. クライアント名の中和（全プロジェクト共通）

クライアント組織を示す企業名（Microsoft、Google等）を検索・除去。

- クライアント組織を示す企業名は削除。残余文が完全・自然なら単純削除を優先。
- 例：`Microsoft Datacenter Work Rules and Regulations` → `Datacenter Work Rules and Regulations`。日本語訳も `Datacenter Work Rules and Regulations` に直接言及。`クライアント` を追加しない。
- 文に組織/責任者/承認者/所有格/文法主語が必要な場合のみ `Client`/`クライアント` を使用。
- 実クライアント名を別実クライアント名に置換しない。
- OEM・請負業者・ソフト/製品名・法定機関・その他非クライアント実体を示す企業名は変更しない。
- 役割が曖昧なら推測せずレビューに回す。
- 検索範囲は本文段落のみでなく、表セル・ヘッダ/フッタ・テキストボックス・シェイプ・SmartArt・コメント・リレーションシップ等の関連パッケージパーツを含む（`Document.paragraphs` のみ不十分）。

## 5. 共通バイリンガル提示規則

- 既存の文書構造・行順・ナンバリング・結合セル・チェックボックス・サインオフ欄・警告・バックアウトセクションを保持。
- バイリンガルセルでは英語先行、日本語を直後の新段落/改行として配置。
- 言語ブロックは最初の文ではなく論理グループ単位で定義。指示の後に英語の経路/オプション/タグ/盤/機器行が続く場合、それらは英語ブロックの一部。完全な日本語指示と対応日本語経路/タグ行は完全英語グループの後にのみ配置。
- 翻訳可能な操作セクション/Part見出しは `English heading / 日本語見出し` のインライン形式（プロジェクト別の全角/半角規則に従う）。見出しの整列・強調を保持。リテラル機器/HMIラベルを変える場合はインライン形式を使わない。
- 機器タグ・システム識別子は不変：`52RA`/`89RB1`/`TR1B`/`PME`/`ECMS`/`FOC`/`CFM`/`UPS`/`VCB`/`ACB`/`CRAH`/`BMS` 等は局所化しない。
- アプリケーションパスを完全保持（大文字小文字・区切り含む）：`PME > DIAGRAMS > OVERVIEW`。
- 各状況分岐内で完全な該当HMI/アプリケーションパスを反復。`同画面にて` 等の曖昧言い回しで置換しない。
- Location/Equipment列値は固定データとして翻訳しない。部屋名・機器名・盤名・タグ・資産ラベルを原文のまま保持。
- 盤ラベル・アラームテキストを実表示のまま保持。日本語説明が必要な場合はリテラルラベルを引用符で保持し周辺指示のみ翻訳。
- チェックボックス記号とその関連付けを保持。`ON`/`OFF`/`OPEN`/`CLOSED`/`Auto`/`Manual` はリテラル盤表示なら翻訳しない。参照スタイルが要求する場合のみ括弧書きで日本語追加。
- タッチパネル操作はボタンテキストを完全保持し `「[label]」ボタンを押す。` を使用。メニュー/ステータス文字列を完全保持。
- テキスト色を対応日本語訳で保持。英語が赤/緑/他の意図的色なら同じRGB/テーマ色を適用。部分着色（赤の警告/緑のHMI経路等）は該当日本語セグメントのみ着色。
- 原文の整列を保持。中心英語は中心日本語。垂直整列も保持。通常操作は明示的中心付けがない限り左揃え。セル垂直中心が水平中心を許可しない。
- 英語アクションと日本語訳の間に空段落を挟まない。別論理状況/内容ブロック間の空段落は最大1つ。連続する可視空段落を削除（フォーマットと英語→日本語→ビジュアルの順序を保持）。
- 手順ステップ段落は1.0行間隔・前後0pt（承認された例外を除く）。継承段落スタイルに依存しない。
- 写真/ネスト表は元の手順セル内に物理保持。写真は `wp:inline`、フローティングアンカーにしない。両方ある場合は関連表の後に配置。行が高すぎる場合 `cantSplit` や固定/正確行高制約を削除しWordがページをまたげるようにする。フィットさせるためだけに写真をリサイズ/切離/別行移動しない。
- target-equipment selectionセル（`Circle`/`Mark`/`Tick the target equipment`）は保護原文データ。当該SOP原文から完全セル構造をコピーし日本語指示のみ挿入。カテゴリ見出し・チェックボックス・機器名・資産タグ・順序・綴り・空白・ネスト表構造を保持。前SOPから機器リストをコピー/適応しない（テンプレが同一に見えても）。
- Field Comments・notes・expected outcomes・サイドリスト・その他内容-bearing列の操作内容を翻訳（明示的除外がない限り）。チェックボックス・リストフォーマットを保持。
- フローチャートの意味文字列をすべて翻訳（箱外テキスト・分岐ラベル・経路キャプション・コネクタ注釈・凡例含む）。日本語は対応英語の直下に配置。原文位置とコネクタ間隔を保持。
- Part見出しは静的可視テキスト。`REF ... \h` フィールドでブックマーク欠落の場合、キャッシュ見出しを通常フォーマット済みテキストに平坦化（Part H 以降で文書先頭にジャンプしないよう）。
- 長い手順表のフローティング表配置 `w:tblpPr` と `w:tblOverlap` を削除しインライン化。Wordがページ付けで前Partを視覚的に反復/再開しないよう。各Partが1回・全ステップIDが一意か確認。

## 6. 共通QAチェックリスト

### 技術的忠実度
- 全ステップ・条件・期待結果・警告・責任者・場所・タグ・状態・タイミング値・単位が両言語に存在。
- 機器タグ・アラーム名・HMIパス・図面参照・文書番号が原文と厳密一致。
- target-equipment selectionセルが当該SOP原文と厳密一致。他SOPからの継承/ドロップなし。
- クライアント実企業名が残っていない。削除は自然。`Client`/`クライアント` は意味/文法に必要な場合のみ。製品/OEM/請負業者/機関名は厳密保持。
- `OPEN/CLOSED`/`ON/OFF`/入出力/前後/隔離-復旧/主-予備方向を独立検証。
- 全比較演子と限界（`<`/`≤`/`>`/`≥`/範囲/時間/%/温度/圧力/電圧値）が英語/日本語で一致。
- 遠隔指令・現地アクション・期待自動応答・検証ステップを混同しない。
- LOTOステップはロック所有権・タグデータ・試験点・電圧クラス・残留エネルギー放電・試運転要件を保持。
- 化学物質取扱ステップは該当SDSとプロジェクト/QHSE要件で検証。
- 不明英語を流暢にするための技術的仮定を挿入しない。

### 言語一貫性
- 制御 `〜する。／〜ことを確認する。` 体裁。
- 反復英語フレーズは同一日本語訳（文脈が真に異なる場合を除く）。
- リテラル画面/盤ラベルは保持し、叙述訳と明確に区別。
- 英語略語は保持。日本語展開は有用かつ一貫する場合のみ。

### 文書整合性
- 表構造・結合セル・行ナンバリング・チェックボックス・サインオフ欄・警告・バックアウトセクションを保持。
- 日本語テキストは対応英語と共に配置。隣接誤行/誤セルに配置しない。
- 切抜き/隠蔽/重複/チェックボックス/欄から分離されたテキストがない。
- ヘッダ/フッタ/リビジョンデータ/ページ番号/文書タイトルが正確。
- Document Control/Annual Reviewセクションは原文のまま（プロジェクト別ルールで別途指定がない限り）。
- 管理・事前実行フォームセクションは `projects/<project>.md` の指定に従い英語維持。
- Location/Equipment列値は原文のまま。
- Field Comments等の翻訳対象内容は文書化された除外がない限りバイリンガル。チェックボックス/リストフォーマット保持。
- ネイティブSmartArtは別段落で英→日。ラスターフローチャートは元ビジュアルシステムを保持しつつインラインバイリンガルテキスト追加。
- 全意味フローチャートラベルがバイリンガル（分岐キャプション/経路ラベル/注釈/凡例/箱外含む）。
- 図入り手順ステップは 英語ブロック→日本語ブロック→関連写真（全写真は最後）。
- 各日本語訳は対応英語の意図的色強調を保持。
- 内部サブ見出しは下線インラインバイリンガル見出し1回として出現。本文/アクション段落に下線が誤って継承されていない。
- 多分岐ステップは `バイリンガル分岐見出し→英語アクション→日本語アクション` を各分岐で反復。条件と訳を共に保持。
- 写真/ネスト表は原文操作セル内に保持。高いビジュアル行はページをまたげる。
- 空Expected Outcomeセルは推論せず、納品後レビューリマインダーに記載（プロジェクト別ルールで自動補完を指定しない限り）。
- 全プレースホルダ・レビュアー問い合わせは解決または可視的にリスト化。
- Word修復ファイルの場合、修復パッケージから生成され、未修復XMLパーツは復元されていない。

## 7. 監査スクリプトの実行

```bash
# 構造監査（原文と出力を比較）
python scripts/audit_docx.py SOURCE.docx OUTPUT_JP_EN.docx

# target-equipment selection照合（該当ステップがある場合）
python scripts/audit_equipment_lists.py SOURCE.docx OUTPUT_JP_EN.docx
# exit 0 = 完全一致、exit 1 = 不一致（必須FAIL）

# 書式正規化（全挿入完了後・納品前に必須・べき等）
# 挿入JPランのフォントをプロジェクト本文フォントに統一、本文=非太字、
# 見出し(" / "区切り)=太字、破損サイズ(w:sz>36)を本文サイズに修正
python scripts/normalize_format.py OUTPUT_JP_EN.docx [--font "Meiryo UI" --body-size 18]

# 書式QAゲート（違反1件でも exit 1 = 納品不可）
# フォント統一・本文太字・破損サイズを検出
python scripts/audit_format.py OUTPUT_JP_EN.docx [--font "Meiryo UI" --max-size 36]

# 部分色強調の継承（原文ENに部分着色がある場合・必須）
# EN着色リテラル（SOP参照・HMIパス等）をJP訳内で同色+太字に分割着色
python scripts/inherit_color_emphasis.py OUTPUT_JP_EN.docx

# ラスターフローチャートのバイリンガル化（overlay方式・2ステップ）
# 1) OCR支援: 色箱矩形+英語ラベルbboxのJSONダンプ → "jp"を記入
python scripts/build_flowchart_bilingual.py --ocr SRC.png --dump labels.json
# 2) 重ね描き+DOCX差し替え（--mediaはword/media/imageN.*のファイル名）
python scripts/build_flowchart_bilingual.py --src SRC.png --labels labels.json \
    --docx OUTPUT_JP_EN.docx --media image2.png
```

依存：`python-docx`、`lxml`、`Pillow`、`numpy`（OCR支援のみ`easyocr`）。

```bash
pip install python-docx lxml pillow numpy easyocr
```

**書式ゲートは省略不可**：`deepcopy` ベースの挿入は元ランのフォント/太字/サイズを無条件継承するため、正規化なしだと宋体/メイリオ/Calibri混入・本文太字・110pt(`sz=220`)級の破綻が必ず混入する（SOP-308/309/310事故）。`normalize_format.py` → `inherit_color_emphasis.py`（部分着色がある場合）→ `audit_format.py` PASS を毎回確認する。`--font` はプロジェクト別（KSW=Meiryo UI、KIX1は別途）に指定。
